### Template

For each endpoint:

```
METHOD /path
Auth: <public | logged-in | admin | team_member | admin-or-team-member | customer-with-gallery-session>
Ownership check: <what beyond role, if anything>
Request: <body fields or query params>
Response: <what data comes back>
Success code: <200/201/204>
Errors: <which 4xx and when>
```


### Design assumptions

- Admin: Creates events, manages team members, reviews photos, and manages galleries.
    
- Team member: Can access assigned events and upload photos to those events.
    
- Customer: Has no account; accesses a published gallery using its PIN.
    
- Ownership check: Covers resource-level access beyond simply having the required role.
    
- Gallery session: A short-lived session created after successful PIN verification. It is separate from the admin/team-member login session.
    
- Photo storage: Original photos are stored in S3. Uploads use presigned PUT URLs; downloads use presigned GET URLs.
    

# Updated API Design

### Design assumptions

- Admin: Creates events, manages team members, reviews photos, and manages galleries.
    
- Team member: Can access assigned events and upload photos to those events.
    
- Customer: Has no account; accesses a published gallery using its PIN.
    
- Ownership check: Covers resource-level access beyond simply having the required role.
    
- Gallery session: A short-lived session created after successful PIN verification. It is separate from the admin/team-member login session.

# Group 1 — Auth

## 1. Register admin

```
POST /api/auth/register
Auth: public
Ownership check: None

Request:
{
  name,
  email,
  password
}

Response:
{
  user: {
    user_id,
    name,
    email,
    role: "admin",
    created_at
  },
  message: "Admin registered successfully"
}

Success code: 201

Errors:
400 if required fields are missing or invalid
400 with error code PASSWORD_TOO_SHORT if password has fewer than 8 characters
409 if email already exists
```

### Notes

- Store the password as `password_hash`, never as plaintext.
    
- The `role` must be `admin`.
    
- The `name` field is required by the `users` table.
    

## 2. Login — both roles

```
POST /api/auth/login
Auth: public
Ownership check: None

Request:
{
  email,
  password
}

Response:
{
  user: {
    user_id,
    name,
    email,
    role: "admin" | "team_member"
  },
  message: "Login successful"
}

Success code: 200

Errors:
400 if email or password is missing
401 if credentials are invalid
403 if account is inactive, if account-status handling is implemented

Security notes:
- The session token is returned through the Set-Cookie response header.
- Cookie attributes:
  HttpOnly
  Secure
  SameSite
- The session token must not be included in the response body.
- Rate limit by email and IP using Redis.
- Allow 5 failed attempts per email + IP within 15 minutes.
- The 6th failed attempt returns 429.
- Return a Retry-After header with the 429 response.
```

### Example response header

```
Set-Cookie: session_token=<token>; HttpOnly; Secure; SameSite=Lax; Path=/
```

> The database schema does not include an account-status column. Therefore, the `403 account inactive` behavior requires an additional account-status mechanism or should be removed if inactive accounts are not supported.

### Supported content type
- `image/jpeg`
- `image/png`
- `image/webp`
- `image/heic` (iPhone)

#### Max size = 20MB — 20 * 1024 * 1024 bytes


### Internal database operation

The server creates a photo record with:

```
photo_id: generated by database
event_id: requested event
uploaded_by: authenticated user's user_id
filename: request.filename
s3_key: internally generated storage key
file_size: request.file_size
created_at: current timestamp
photo_status: "pending"
content_type: request.content_type
updated_at: current timestamp
```

### Important response restriction

The following internal field must not be returned:

```
s3_key
```

The presigned upload URL is sufficient for the client to upload the file.

### Transaction behavior

The operation must be all-or-nothing.

If even one photo ID is invalid:

- No photo is added.
    
- The transaction is rolled back.
    
- The response lists the invalid IDs.
    
- There is no `skipped_photo_ids` field.

```

- Removed `skipped_photo_ids`.
    
- Removed the restriction against modifying a published gallery.
    
- Published galleries can be modified.
